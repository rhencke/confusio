# 03 — Schema Loading, SDL Storage, and Type Validation Strategy

## What this document covers

The GraphQL executor (see [04-executor.md](04-executor.md)) needs a type registry at
runtime for three purposes:

1. **Introspection**: answer `__schema` and `__type` queries directly, without touching a
   backend REST call.
2. **Leaf detection**: decide whether a field selection must have sub-selections (object,
   interface, union) or must not (scalar, enum).  This drives executor dispatch.
3. **Field existence validation**: catch unknown fields before any backend call is made and
   return a GraphQL validation error.

This document covers how the schema is vendored, processed into a Lua table, stored, and
queried at runtime.  Argument type checking and variable coercion are covered in
[04-executor.md](04-executor.md).

## Two-file split: data vs. API

The schema module is split into two files:

| File | Role |
|------|------|
| `internal/graphql_schema_data.lua` | Auto-generated; contains the raw type data as a large Lua table literal.  **Never edited by hand.** |
| `internal/graphql_schema.lua` | Hand-written; loads the data table and exports the runtime API functions. |

This split means the generator script (`scripts/gen-graphql-schema.py`) only ever touches
the data file.  The API code and its tests remain stable across schema updates.

## SDL vendoring

### Source

GitHub publishes its canonical GraphQL schema as SDL at:

```
https://docs.github.com/public/fpt/schema.docs.graphql
```

This file is vendored at:

```
vendor/
  github-graphql-schema/
    schema.docs.graphql   — GitHub's published SDL (committed; not regenerated at build time)
    LICENSE               — MIT licence from the upstream repo
    README.md             — instructions for updating the snapshot
```

The `vendor/github-graphql-schema/README.md` should mirror the pattern used for the REST
spec:

```bash
curl -fsSL https://docs.github.com/public/fpt/schema.docs.graphql \
  -o vendor/github-graphql-schema/schema.docs.graphql
```

### Phase 1 subset

The full GitHub SDL is approximately 600 KB of text covering ~490 named types.  Bundling
the full schema into `confusio.com` would add ~200–300 KB to the binary after compression.

For Phase 1, the generator script produces a **reachability subset**: starting from the
`Query` and `Mutation` root types, it traverses field type references recursively and
includes only the types actually reachable from those roots.  Built-in types (`__Schema`,
`__Type`, `__Field`, `__InputValue`, `__EnumValue`, `__Directive`) are always included
for introspection.

Types outside the reachability closure are omitted from the data file.  A client that
requests a field whose parent type is in the subset but resolves to an omitted type will
receive a schema-validation error; this is acceptable for Phase 1.

The complete SDL is kept in `vendor/` as the source of truth; the subset is a derived
artifact.

## Schema generation script

```
scripts/gen-graphql-schema.py
```

Reads `vendor/github-graphql-schema/schema.docs.graphql` and writes
`internal/graphql_schema_data.lua`.

### Script responsibilities

1. Parse the SDL (Python's `graphql-core` library, available via a dev-time pip install, or
   a hand-written SDL tokeniser — the script need not run inside Redbean).
2. Build the reachability set from `Query` and `Mutation`.
3. Emit `internal/graphql_schema_data.lua` with a `graphql_schema_data` global table
   (see format below).
4. Write a header comment recording the source file path and schema version so diffs are
   self-documenting.

The script is run manually (`make generate-schema`), not during `make build`.  The
generated file is committed to the repository, exactly as the Makefile-generated
`.make-families.mk` is committed.

### Validation target

```
make validate-schema
```

Reruns the generator and diffs the output against the committed file.  Fails if they
differ.  Wired into `make test` so CI catches schema-data drift.

### Type reference string encoding

Type references are stored as strings mirroring GraphQL's SDL type notation:

| String | Meaning |
|--------|---------|
| `"String"` | nullable String scalar |
| `"String!"` | non-null String scalar |
| `"[Issue]"` | nullable list of nullable Issue objects |
| `"[Issue!]"` | nullable list of non-null Issue objects |
| `"[Issue!]!"` | non-null list of non-null Issue objects |

The string encoding is compact, human-readable in diffs, and unambiguous.  The schema API
module expands these strings to nested introspection tables on demand (see below).

### Built-in scalars

The five built-in GraphQL scalars are always present even if not in the vendored SDL:

```
String, Int, Float, Boolean, ID
```

The generator adds them explicitly if the SDL omits them (SDL authors often rely on the
spec's implicit inclusion).

### Introspection meta-types

The six introspection types (`__Schema`, `__Type`, `__Field`, `__InputValue`,
`__EnumValue`, `__Directive`) are always included verbatim, populated with the definitions
from the GraphQL spec.  They are the same for every GraphQL server.

## Runtime API (`internal/graphql_schema.lua`)

Exports (globals):

```lua
-- Look up a named type.  Returns type_def table or nil.
graphql_schema_type(name)

-- Look up a field definition within a named type.
-- Handles built-in meta-fields (__typename, __schema, __type) automatically.
-- Returns field_def table or nil.
graphql_schema_field(type_name, field_name)

-- True if the resolved (unwrapped) type is a scalar or enum leaf.
-- type_ref is a type-reference string ("String!", "[Issue!]!", etc.).
graphql_schema_is_leaf(type_ref)

-- Extract the innermost named type from a type reference string.
-- "String!"       → "String"
-- "[Issue!]!"     → "Issue"
-- "[IssueState]!" → "IssueState"
graphql_schema_base_type(type_ref)

-- True if the type reference is non-null at the outermost level.
graphql_schema_is_nonnull(type_ref)

-- Expand a type_ref string to the nested table form required by introspection.
-- "String!"    → { kind="NON_NULL", name=nil, ofType={ kind="SCALAR", name="String", ofType=nil } }
-- "[Issue!]!"  → { kind="NON_NULL", ofType={ kind="LIST", ofType={ kind="NON_NULL", ofType={kind="OBJECT",name="Issue"} } } }
graphql_schema_expand_type(type_ref)

-- Return the full __schema introspection response table.
-- The response shape matches GitHub's IntrospectionQuery response exactly.
graphql_introspect_schema()

-- Return a single __type introspection response table for the named type.
-- Returns nil if the type is not in the registry.
graphql_introspect_type(name)
```

### `graphql_schema_base_type` implementation note

```lua
function graphql_schema_base_type(type_ref)
  -- The innermost named type is the first (and only) run of [_A-Za-z][_0-9A-Za-z]* chars.
  return type_ref:match("[_%a][_%w]*")
end
```

### `graphql_schema_expand_type` implementation note

```lua
function graphql_schema_expand_type(type_ref)
  if type_ref:sub(-1) == "!" then
    return { kind = "NON_NULL", name = nil,
             ofType = graphql_schema_expand_type(type_ref:sub(1, -2)) }
  elseif type_ref:sub(1, 1) == "[" then
    return { kind = "LIST", name = nil,
             ofType = graphql_schema_expand_type(type_ref:sub(2, -2)) }
  else
    local t = graphql_schema_type(type_ref)
    return { kind = (t and t.kind or "SCALAR"), name = type_ref, ofType = nil }
  end
end
```

### Meta-field injection

`graphql_schema_field` must return synthetic definitions for the three built-in meta-fields
that appear on every object and interface type:

| Field | Type |
|-------|------|
| `__typename` | `String!` |
| `__schema` | `__Schema!` (only on `Query`) |
| `__type` | `__Type` (only on `Query`, arg: `name: String!`) |

The executor uses `graphql_schema_field` to check every field it encounters; these must
resolve to leaf/composite correctly even though they are not declared in the SDL.

## Load order

`graphql_schema_data.lua` is raw data with no dependencies.
`graphql_schema.lua` depends on the data.  Both are loaded before the executor.

Insert in `.init.lua`:

```lua
dofile("/zip/internal/graphql_parser.lua")
dofile("/zip/internal/graphql_schema_data.lua")   -- new (generated)
dofile("/zip/internal/graphql_schema.lua")         -- new (hand-written)
dofile("/zip/internal/families.lua")
```

The `dump-endpoints.lua` and `dump-claims.lua` scripts stub out backend loading but must
allow `graphql_schema_data.lua` to load — it contains no Redbean API calls and requires no
stub treatment.

## Type validation in the executor

Full GraphQL validation (as specified in the spec's "Validation" chapter) is complex.
Phase 1 implements a targeted subset sufficient to protect the backend from nonsense
requests and to give clients actionable error messages.

### Checks performed (Phase 1)

| Check | Why |
|-------|-----|
| Operation type has a root in the schema (`query_type` / `mutation_type`) | Catch `subscription` which is out of scope |
| Every named field in a selection set exists on the parent type | Catch typos; avoids making a REST call for a field that can never resolve |
| Leaf fields (scalar, enum) have no sub-selection set | Mandatory per spec; simple to check |
| Composite fields (object, interface, union) have a sub-selection set | Mandatory per spec |
| Fragment type conditions name a known type | Avoids crashing the executor on unknown type names |

### Checks deferred to a later phase

| Check | Reason for deferral |
|-------|---------------------|
| Argument name and type correctness | High complexity; REST translators already ignore unknown arguments |
| Variable type compatibility with usage sites | Requires full type coercion logic |
| Fragment cycles | Requires a graph cycle check; unlikely in practice from real clients |
| Directive location validity | `@skip`/`@include` are always valid on fields and fragments |
| Input object coercion | Mutations only; deferred to Phase 2 |

Validation errors are returned in the GraphQL error envelope (see
[09-errors.md](09-errors.md)) with the `locations` and `path` fields populated where
possible.  A validation error short-circuits execution: no REST calls are made.

## Schema updates

When GitHub updates its schema, the update procedure is:

1. Run `make update-graphql-schema` (equivalent of the REST spec update in
   `vendor/github-rest-api-description/README.md`) to fetch the new SDL.
2. Run `make generate-schema` to regenerate `internal/graphql_schema_data.lua`.
3. Run `make test` — `validate-schema` confirms the committed data matches the SDL.
4. Review the diff: new fields are additive and safe; removed/renamed fields may break
   executor resolvers and should be treated as a compatibility concern.
5. Commit both the new SDL and the regenerated data file together.

## Testing

Unit tests in `test/graphql-schema.lua` (run via `redbean.com -i`):

- `graphql_schema_type("Repository")` returns a table with `kind = "OBJECT"`.
- `graphql_schema_type("IssueState")` returns a table with `kind = "ENUM"`.
- `graphql_schema_type("NonExistent")` returns `nil`.
- `graphql_schema_field("Repository", "issues")` returns a field with `type = "IssueConnection!"`.
- `graphql_schema_field("Query", "__schema")` returns the synthetic meta-field.
- `graphql_schema_field("Repository", "__typename")` returns the synthetic meta-field.
- `graphql_schema_is_leaf("String!")` → `true`.
- `graphql_schema_is_leaf("Repository!")` → `false`.
- `graphql_schema_is_leaf("IssueState")` → `true` (enum is a leaf).
- `graphql_schema_base_type("[Issue!]!")` → `"Issue"`.
- `graphql_schema_expand_type("String!")` produces the expected nested table.
- `graphql_schema_expand_type("[Issue!]!")` produces three levels of wrapping.
- `graphql_introspect_schema()` returns a table with `queryType.name = "Query"`.
- `graphql_introspect_type("IssueState")` returns a table with `kind = "ENUM"` and a
  `enumValues` array containing `"OPEN"` and `"CLOSED"`.
